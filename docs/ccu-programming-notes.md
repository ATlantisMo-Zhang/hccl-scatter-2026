# CCU 编程踩坑笔记

比赛过程中积累的 CCU（Compute Communication Unit）编程经验。昇腾 950 仿真环境下，这些约束决定了代码能不能跑、跑多快。

## 1. 任务图与三层证据

CCU kernel 注册后由翻译器展开为任务图（SQE 指令序列）。判断代码行为有三层证据，不能互相替代：

1. **源码层**——你以为的执行顺序
2. **展开层**——翻译器实际生成的指令（同一 mainBlock 的 LoadArg 会被翻译器先收集再统一翻译，把 LoadArg 挪进 `CCU_IF` 分支不会改变实际加载时机）
3. **关键路径层**——平台实际耗时在哪段

很多"看起来是优化"的改动只动了第 1 层。本地验证必须导出实际任务图核对（HCCL-VM 的 SQE 数据库可以还原每次调用的完整依赖图）。

## 2. 通知（Notify）协议设计

跨 rank 同步全靠 Channel 上的 Notify 位 + Event。我们的位分配：

```
bit 1|2   READY（接收者发布 output/token 地址）
bit 3     WRITTEN（root 数据写完）
bit 4     CONSUMED（接收者确认，小消息协议可省）
bit 5     STAGED（中转 staging 完成）
bit 6     FORWARDED（helper 转发完成）
bit 7|8   RELAY_DONE / 确认（中转尾段握手）
bit 9|10  PLAN（helper 编号与长度下发）
```

关键约束：

- **EventWait 是消费型等待**：等待后对应位被清掉，每个位只能等一次。流水或多生产者场景必须用多 event 或位掩码隔离（我们的 `sent`/`staged`/`restored` 三个 event 各管一类写）。
- **跨调用复用要闭合因果链**：同一个通知位在下一轮调用会复用。必须保证"旧 Wait 先于同目标槽的新 Record"——靠每个生产者的新 Record 依赖消费旧数据的 Wait 来传递。换 root、换方向时按物理端点逐条核对，不能假设"位 3 永远是 WRITTEN"。
- **零数据调用不产生通知**：zero 分支直接返回，不能留下旧通知位被误读。
- **root 可能早于 receiver 返回**：不能默认全 rank 同步结束，完成边界要由显式通知覆盖。

## 3. 双 Die 拓扑约束

2×8/4×3 的 rank 分布在两个 IO Die：

- 单个 kernel 内的 channel 必须归属同一 die；跨 die 通信是独立 kernel + 显式完成依赖
- Host 侧每个 die 最多注册 2 个 mission（kernel 句柄），第三个会注册失败
- 双 die 并行需要 Host 双线程：主线程下发 die0、slave 线程下发 die1，全部下发后再 join。**线程 Notify 与 Channel CKE 是两套独立资源**，线程间同步（Notify 0）不占用 channel 通知位
- slave 线程任务图有 ABI 约束：首任务必须是本地 WAIT、尾任务必须是 RECORD，否则报错

## 4. 资源与句柄

- `GetResByChannel<Variable>(ch, XN)` 的变量槽按 XN 编号分配，复用已有槽时要错开通知掩码位
- CCU Variable 不能随意拷贝/新建——地址算术用 `v += offset` 原地扩展，绑定已有句柄
- 输入输出地址每次调用都要重新查 token（`HcommCcuGetMemToken`），token 是每轮有效的内存访问凭据，不查会访问失败

## 5. 性能直觉（实测校准过）

- **任务数不是瓶颈**：F3 把 SQE 从 893 压到 532，大消息用时不动；初赛 255304 任务数 181→291 反而快 22%
- **等待位置决定性能**：F8 只改发送次序（任务和数据量不变）换 22%；A21 在链路满载后改等待位置只换 0.4%——同样"消除串行等待"，数据路径是否饱和决定收益大小
- **小消息任务数量敏感**：<16MiB 时每多一次 kernel 启动、每多一轮通知往返都是硬成本；大消息只看最忙链路
- **图上并行 ≠ 硬件重叠**：依赖图允许重叠只证明"可以"，共享带宽会吃掉理论收益。判断依据是"哪段工作决定最终完成"

## 6. 验证纪律

每个候选在官测前过固定矩阵：换 root、换地址、门槛两侧（16MiB-4 / 16MiB）、小→大→小、zero、跨片尾块（工程外 8MiB 测试镜像）、精确 self 同址。全部逐元素数值 + 输入保护 + 输出 guard + Checker。跑分机会只用来回答性能问题，正确性在本地闭合——这套纪律让 23 个版本中没有任何一个坏版本污染过成绩基线。
