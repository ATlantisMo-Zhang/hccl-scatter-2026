## 收益分层：每档收益与机制本质匹配

对 21 点（2×8 大消息代表）做完整分解：

```
F0  1620
F1  1080   -33%    结构收益：双 die 并行
F8   838   -22%    等待收益：发送提前，任务与字节量不变
F11  765   -8.7%   均衡收益：七 helper，达到流量模型平衡点
F13  760   -0.7%   参数微调
A21  757   -0.4%   控制微调（链路已满载，收益趋零）
```

结论：**收益递减不是优化失效，而是空间收敛**。结构、等待、均衡三类大头依次兑现后，剩余空间只在控制依赖和收尾。这个判断来自赛前就建立的流量模型。

## 流量模型：预测与实测互相校准

2×8 大消息的模型（每 rank 数据量 B、机内链带宽 b、root Clos 出口 4b）：

- 必要流量下界：`T ≥ 15B / 11b`
- 七 helper 各代转 rB 时：Mesh 项 `(1+r)B/b`，Clos 项 `(8-7r)B/(4b)`
- 平衡点 r = 4/11，理论传输项较 F8 的 1.5B/b 下降 9.09%
- **F11 实测：20/21 下降 8.69% / 8.71%**

模型的作用不只是预测——它在 F13 之后阻止了继续扫比例的无用功（2/5 比例在模型里反而把 Mesh 项从 1.36 推高到 1.4，实测 <1% 验证了模型）。

## 关键教训：总量少不等于快

- F3 把 SQE 从 893 压到 532，大消息用时几乎不动——任务数量不是瓶颈
- 初赛 255304 总网络量 15B→17B、任务数 181→291，反而快 22%——瓶颈在最忙链路（root 跨机出口）
- 优化前先回答"哪段工作决定最终完成"，而不是数指令、数任务、数字节

## 小消息的独立空间

小点（19/22/25/28，11–14μs 量级）与大点由完全不同的机制主导：

- F2（只启动含 root 的接收组）一次降 2–3μs
- F14（Pull 协议，去掉 root 等齐 READY 的汇合）22 点 14→12
- F18（ReadyPush，省 CONSUMED 收尾）19 点 12→11
- 每次协议级改动只能兑现 1–2μs，参数微调无收益——延迟主导的路径上，每轮通知往返都是硬成本

## 未兑现的候选（账本上的遗憾）

- **2×8 Clos selfCopy 与发送重叠**：任务图确认 root 自身复制串行在全部网络 Write 之后，数据依赖上可与发送重叠。F15 在 4×3 上用"复制迁移"兑现了 2%，2×8 的同源优化因窗口耗尽未实现，理论量级约 2%
- **4×3 小消息 Pull**：两次实现均在换 root 场景出现数值错误，未能交付
