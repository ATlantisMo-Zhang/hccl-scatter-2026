# 赛后复盘：窗口管理教训与方法论沉淀

决赛差一名进入获奖名次（第 18，三等奖取前 17）。这篇复盘回答两个问题：差距在哪里，以及哪些是可以避免的。

## 差距定位

最终 12 点与同屏 TBest 的差距分三类：

| 类别 | 点 | 差距 | 判断 |
|---|---|---|---|
| 大点结构性差距 | 20/21（965/757 vs 941/738）、29/30（1720/1350 vs 1680/1310） | 2.3%–3.0% | 对手整体结构领先，且 20 与 21 的差距比例几乎一致，说明不是单点缺陷 |
| 小点绝对差距 | 19/22/25/28 | 2–4μs（相对 18–31%） | 每轮协议改动只能兑现 1–2μs，越到极限越难 |
| 已持平 | 23/24 | 0 | 从 F1 后始终保护，未因改动回退 |

## 五个教训

1. **多目标同包会烧掉窗口**。F17 把两个独立机制（21 点的等待重排 + 22/25 的小消息 Push）融合提交，组合验证在继承路径上出数值错误，整包报废。其中 21 点候选本身是 3 行级改动、单变量验证成本最低的一个，却因为同包被连累，官测晚了一整轮。正确顺序：**最小改动单变量优先占窗口，组合包只在各单项官测验证之后**。

2. **实现可靠性消耗迭代机会**。23 个版本中 7 个死在本地必要验证（F4/F5/F9/F10/F12/F16A/F17）。每失败一次就少一次官测窗口。失败的准确归因是"实现可靠性"而不是"优化理论连续失败"——其中 F9 提前复制、F16A 换 root 数值错误都是同一类问题：协议改动对跨调用通知复用链的影响验证不充分。

3. **"后备候选"在窗口压力下等于"不做候选"**。2×8 selfCopy 重叠在评阅中排第三顺序，最终没有实现时间。回头看它是账本上唯一还有 2% 量级潜力的方向。候选应按理论收益排序，而不是按实现成本排序。

4. **点号↔拓扑映射全程是推测**。平台不提供逐点 trace，20/21 对应 2×8 大消息的映射靠版本响应反推（F1/F8/F11 的改动命中模式），可信但从未证实。所有优化都建立在间接证据上。值得专门花一轮官测做映射探针。

5. **计分公式与参照不可控**。同样的用时在不同轮次分数不同（同屏参照队伍同用时分数相差 5.2 分），精确公式全程未知。"差一名"的分差本质不可预测，决策只能基于逐点用时而非跨轮总分。

## 方法论沉淀

做对了的：

- 版本可回退 + 失败候选隔离 + 官测包身份核对（SHA256 链）
- 流量模型先行，模型与实测互相校准（F11 预测 9.1% / 实测 8.7%）
- 每个窗口前必要验证前置：官测只回答性能问题，不回答正确性问题
- 验证矩阵固定：换 root、换地址、门槛两侧、小→大→小、zero、跨片尾块
- 逐点账本记录，不因 1μs 波动换版

要改的：

- 官测窗口预算制：一次窗口回答一个问题
- 候选按理论收益排序进入开发队列
- 每天第一件事核对剩余窗口数，按窗口分配候选，而不是按候选数找窗口
- 大小消息的协议演进并行推进，不挤占同一窗口
